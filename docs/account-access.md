The account settings, administration, JWT sessions and three-role access-control system are implemented together. The key design decision is that an authenticated request must still correspond to a current account and a current session. A valid signature alone no longer grants access. This makes an administrator’s edits effective on the next server interaction, including when the edited account belongs to that same administrator.

Settings is a navigation link that requests a new server-rendered document. The Settings landing page exposes User settings to Operators and Admins and exposes Admin dashboard only to Admins. Viewers receive a read-only explanation instead of an account editing link. User settings, the admin landing page, the user list, the account editor and server logs each have their own template under web/templates. They share a layout file and the existing console palette, typography, borders and responsive styling. The main dashboard does not contain the account forms or administrator data. These templates cannot be downloaded through the public CSS mount.

The account pages work through ordinary HTML forms. Each request goes through authentication and role authorization before the server loads or renders the page. Submission goes through the same guards, a bounded form parser, the origin check and a CSRF token tied to the current authenticated session. The server validates inputs, changes the database and returns either an escaped error page or a redirect. JavaScript on these pages is limited to theme switching and refreshing a restored browser page; it does not implement account management or decide who is authorized.

User settings permits changing the login username and password. The current password must be supplied before either change is accepted. An empty new-password field preserves the password, while a supplied password must match its confirmation and meet the 12–72 byte limit. The upper limit respects bcrypt’s input limit rather than silently truncating a password. Usernames accept 3–64 letters, numbers, dots, underscores, @ and hyphens, with a letter or number first. Uniqueness is enforced by the database. Passwords are hashed with bcrypt and are never returned in forms. The self-service path ignores submitted role values and always targets the authenticated account.

The admin dashboard provides Users and Server logs. The user list is paginated and links to server-rendered creation and editing forms. Creation requires a username, password and one of the three roles. Editing can change the username, password or role, including for the signed-in administrator. Every successful edit increments the account’s authorization version and deletes all of its session rows in one transaction. This includes a save that leaves the visible values unchanged. Each editor also submits the version it originally loaded; a stale form is refused so it cannot overwrite a newer administrator’s changes. Permission and actor-version checks are repeated inside account mutation transactions.

Account deletion is a hard delete of the user and their session and notification records. Shared target profiles and findings remain intact. A confirmation checkbox is checked again by the server. Administrators may delete themselves when another administrator remains, and may change their own credentials. The last administrator cannot be deleted or demoted. This prevents losing the application’s administration interface through an ordinary account operation while keeping the bootstrap CLI available for recovery.

The JWT contains sub, jti, ver, iss, aud, iat, nbf and exp. The subject is a random account UUID, and the JWT identifier is a fresh random session UUID. No username, password, email or other directly identifying account field is included. The role is deliberately omitted because authorization reads the current database account. The signature uses HS256 with the existing randomly generated 64-byte signing key. Validation pins the algorithm and application-specific token type, validates issuer and audience, requires the timestamps and account version, validates the UUID identifiers, rejects future or expired credentials and restricts lifetime to at most seven days. Unsupported headers, including remote-key and critical-extension headers, are rejected. Key creation now publishes a complete file atomically without overwriting a key concurrently created by another process. The validation choices follow the algorithm, issuer, subject and audience guidance in [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html).

After cryptographic validation, the request must match an undeleted user with the token’s account UUID and version, a recognized role, and an unexpired session record owned by that user. Consequently, a renamed or deleted account cannot keep using an old token, and recreating a username does not restore its old access. Logout deletes the current session record before clearing the cookie, so a copied cookie is revoked as well. Self-service account changes revoke all sessions and require a fresh login. The API returns 401 for a stale session; protected page requests redirect to login. The dashboard already handles API authentication failures, and SSE now also sends a session-revoked event before closing. Streams recheck before every data event and at two-second intervals while idle. Session expiry is stored in UTC and compared as an instant in SQLite to avoid local-time ordering errors.

The role policy lives in internal/access. Viewer has read permission only. Operator has read and write permission, including normal profile and scan management and its own account settings. Admin adds user administration and server logs. The authenticated API group denies every non-read request to a Viewer, which also covers notification read-state changes and deletion. Login and logout remain available as authentication operations for every role. Account and administration routes have separate permission guards, and server-rendered controls reflect those permissions for usability. The server checks remain authoritative if someone changes the DOM, sends a hand-written request or guesses a URL. Scheduled scans remain service-owned background work, and this release retains the existing shared profile visibility across users.

The server log viewer receives the same standard application log output written to the process stream, together with request and database diagnostics. It retains the newest 2,000 entries in memory, limits each entry to 16 KiB and serves 100 entries per page. The page explicitly explains that this buffer starts fresh after a restart. Concurrent writes and snapshots are protected, and log content is rendered as text through html/template. Request logging excludes query strings and bodies, and GORM parameter logging is disabled. The viewer is restricted to Admins. This feature is an operational log tail; persistent retention continues to belong to the service manager or logging system running the application.

The database migration gives existing accounts opaque identifiers, an initial version and the Admin role because the old CLI explicitly provisioned administrators. A migration ledger ensures that this elevation happens once; a later invalid or empty role cannot be promoted on restart. Newly created accounts default to Viewer in the model and admin form. ICEvirtue-admin supports an explicit --role argument and defaults to Admin for bootstrap compatibility. The disposable dashboard fixture explicitly creates an Admin. Existing username-based JWTs are intentionally invalid after this upgrade, so users must sign in again. HTTPS deployments continue to require the existing --secure-cookies option; changing the signing key requires a restart.

Verification includes the complete Go suite, focused race checks for authentication, account routes, migrations and concurrent log storage, and Chromium browser workflows against a disposable database with scheduling disabled. The route-boundary test walks the actual Chi router and checks authentication and role denials across its registered routes. Additional tests exercise every admin edit type, self-editing, current-password checks, stale forms, CSRF rejection, duplicate usernames, hard deletion, last-administrator protection, logout revocation, role/version invalidation, JWT claim and signature tampering, legacy-account migration and SSE shutdown. Browser checks exercise navigation, account creation, role changes, forced re-login, self-service username/password changes, deletion, live-session invalidation, server log rendering and desktop/phone layouts. Dark and light styles were visually inspected, and the tested browser flows produced no application JavaScript errors.
